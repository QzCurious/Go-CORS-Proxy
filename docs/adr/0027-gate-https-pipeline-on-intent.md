# Gate the HTTPS Pipeline on explicit intent

**Status:** accepted

Gateway Runtime admits an HTTPS Pipeline only when the effective Upstream List Projection contains at least one HTTPS Origin Selector. Without HTTPS Intent, runtime HTTPS Readiness is absent: Gateway does not inspect UserCA for runtime use, retain signing material, schedule its expiry, publish a MITM proxy generation, or include HTTPS PAC routes; CORS Proxy still handles every proxy request and direct-tunnels CONNECT. Host Selectors do not create intent: they always contribute HTTP routes and contribute HTTPS routes only after an HTTPS Origin Selector has admitted a ready pipeline, while Origin Selectors follow their explicit scheme.

An admitted pipeline begins in `assessing` with direct CONNECT behavior and no HTTPS routes, waits for settled UserCA facts without blocking Upstream List adoption, and then becomes `settled`. A coherent assessment with usable facts and matching signing material yields ready HTTPS Readiness; Gateway publishes an immutable CA-backed CORS Proxy generation before adding HTTPS PAC routes. Normal not-usable facts yield Unmet HTTPS Intent guidance, assessment error yields a UserCA Assessment Issue, and usable facts without signing material yield a Signing Material Issue. Start remains fulfilled in each not-ready case. These source-specific details replace the generic HTTPS warning collection, and Installed User CA renewal remains a UserCA fact.

When intent disappears or readiness is lost, Gateway first adopts and serves the PAC Projection without HTTPS routes and enqueues its independent Managed PAC publication, then publishes an immutable direct CORS Proxy generation, cancels the ready assessment's deadline, and discards its retained signing material. Intent removal also removes the pipeline detail; readiness loss retains the admitted pipeline as settled not-ready with its source-specific detail. Gateway does not wait for OS reconciliation or PAC clients to refresh. Existing requests are not drained. Pipeline assessments belong to one Gateway-owned pipeline generation: cancellation is best effort, and results from stopped, removed, or replaced pipeline work are discarded. An intent transition arriving during admitted CA mutation remains assessing and direct until the mutation settles.

CORS Proxy constructs one immutable direct or MITM handler generation and owns only request behavior, including CORS repair, preflight responses, goproxy CONNECT behavior, and each MITM generation's bounded certificate cache. Gateway owns the stable listener, HTTP server, outbound transport and its shutdown, active-generation publication, serving goroutines, start/stop, and all pipeline sequencing. Constructing and publishing a generation from validated material is infallible; leaf-generation, signing, and TLS handshake failures remain connection-local.

Install and uninstall remain independent CA Lifecycle Commands. Install without an active pipeline has no runtime HTTPS consequence; with an active pipeline, its CA result remains authoritative and separately carries the resulting HTTPS Pipeline Detail. Uninstall first performs the no-HTTPS PAC transition and direct-generation publication before removing trust and material; incomplete removal remains an uninstall result and CA cleanup issue rather than an HTTPS warning.

This supersedes ADR-0026's intent-independent readiness and proxy-generation lifecycle placement, ADR-0017's always-present latched runtime readiness, ADR-0019's unconditional live-install runtime adoption, and ADR-0022's unconditional runtime expiry coordination. ADR-0026's stable listener, immutable whole-handler generations, per-generation certificate cache, goproxy-owned leaf generation, connection-local failures, and no-drain semantics remain accepted. Gateway's PAC publication is asynchronous and remains independently serialized as decided by ADR-0014 and ADR-0024.
