# Separate Gateway semantics from HTTP representation

The Gateway Module is the sole authority for operation-specific result kinds, semantic details, retryability, next actions, and whether a command fulfilled its requested postcondition; every anticipated command condition is a Surface-Neutral Command Result, while an error means Gateway could not produce a coherent semantic result. CLI and HTTP are control-surface adapters that translate this interface without redefining it. Gateway result wrappers therefore carry no HTTP status or wire-error concerns and are never serialized directly; stable request and detail value records may retain conventional JSON field names when their meaning and shape are identical across the Gateway and HTTP representations.

The Gateway Router returns fulfilled results with a bare operation-specific 2xx body and no success envelope, while every non-success response uses one Gateway Error Response containing a stable code, non-authoritative message, and optional typed details. Codes for unfulfilled results remain operation-scoped because the route already identifies the operation; Router-wide codes represent malformed, authentication, infrastructure, or other failures where Gateway produced no result, and the Gateway Client reconstructs only recognized operation-scoped codes as results without parsing message text.

We rejected a global success envelope, echoed operation names, always-200 command results, route-specific error shells, directly serialized Gateway results, recursively mirrored HTTP detail types, and string-based error recovery. The HTTP Adapter introduces a private type only where the wire shape actually differs, rather than copying an isomorphic tree. This keeps successful bodies focused on their subject, preserves ordinary HTTP success and failure handling, centralizes command meaning in Gateway, and allows meaningful HTTP representation changes without ceremony for identical value records.
