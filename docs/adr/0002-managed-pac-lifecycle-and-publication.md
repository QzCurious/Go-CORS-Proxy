# Managed PAC lifecycle and publication

The activation-consent and user-accepted service-set portion of this decision is superseded by [ADR-0009](./0009-automatic-managed-pac-activation.md). The projection-publication model is superseded by [ADR-0011](./0011-gateway-traffic-projection-and-pac-delivery.md): Managed PAC now delivers the already-served PAC independently to each Network Service rather than deciding which projection is published. The ownership, fixed service set, serial mutation, retry, warning, observation, and cleanup decisions below remain in force where they do not conflict with ADR-0011.

Managed System Proxy uses PAC Routing so unrelated traffic remains direct. Each Gateway Runtime activation separately discovers every visible network service and observes its PAC setting, proposes every successfully observed marker-owned or empty service together, exposes foreign or unobservable services as excluded, and fixes the accepted nonempty Managed PAC Service Set for that runtime. Network-service discovery failure prevents the assessment because no complete service scope is known. Initially excluded and newly visible services wait for another activation, while every later operation freshly classifies fixed members and a selected service can recover from an observation issue on a later PAC Projection without renewed consent.

Gateway gives Managed PAC each accepted, already-derived PAC Projection. Managed PAC owns publication generation, versioned ownership-marked URLs, capacity-one latest-value reconciliation, serial mutation policy, retry, drift classification, current per-service warnings, and observation issues; it drives the PAC Settings external-system module for separate platform-neutral network-service listing, PAC-setting lookup, and mutation. Managed PAC freshly observes each selected setting before deciding whether to invoke a separate platform mutation. During publication, a selected service absent from fresh discovery is skipped, an observed foreign setting is preserved and reported as drift, and any failed PAC-setting observation is reported as a current observation issue without classifying its cause. Observation issues complete without internal retry and wait for a later PAC Projection; any failed platform mutation remains an update failure handled by reconciliation retry without classifying its cause. Every accepted projection is published even when it preserves effective routes, so warning-only Upstream List changes may advance the publication generation. Gateway Runtime exposes the latest Managed PAC Runtime State, warning snapshot, and observation issues through command results and status.

Initial publication begins only after Gateway Runtime and its PAC Endpoint are serving. Mutation failure is nonfatal, preserves the fixed service set and desired projection, reports current warnings, and retries without stopping Gateway Runtime; per-service observation issues are reported but do not make publication fail.

Active-state cleanup separately discovers visible network services, then freshly observes, disables, and verifies every successfully observed enabled marker-owned setting without changing reconciliation admission. Network-service discovery failure leaves the PAC cleanup subject unknown and fails cleanup. A per-service PAC observation issue is disclosed in fulfilled cleanup detail but remains outside the cleanup scope and does not prevent success; a setting that disappears, becomes inactive, or becomes foreign needs no further cleanup. Mutation failures are retained only when verification finds observed active owned residue, which is reported for a later cleanup rather than retried in a tight loop. Uninstall is the complete teardown barrier: it closes admission, discards pending work, quiesces the current writer, performs active-state cleanup, and clears runtime state only after successful teardown; ownership authorizes cleanup regardless of publication generation, while disabled retained URLs, foreign settings, and unobservable PAC settings are not active residue.
