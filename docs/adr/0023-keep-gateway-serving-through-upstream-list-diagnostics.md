# Keep Gateway serving through Upstream List diagnostics

**Status:** accepted

Upstream List format and observation failures are non-fatal to Gateway Runtime. Gateway starts with an empty effective list before receiving a Projection, thereafter retains the last Projection it adopted through either kind of failure, and keeps CORS Proxy and PAC serving while presenting projection and observation diagnostics independently. A sealed Source transition sum distinguishes `Projection`, `InvalidFormat`, and `ObservationError`: Projection replaces the effective list and clears both diagnostics; Invalid Format means readable contents could not produce a complete projection, retains the effective list, and clears any earlier Observation Error because the successful read proves observation recovered; Observation Error means observation could not reliably assess the file and retains both the effective list and the latest projection assessment. Observation Error classifies recoverable read failure, recoverable uncertainty, and terminal stopping without exposing the filesystem observer's types. Malformed individual selectors remain warnings within a Projection; Invalid Format is reserved for whole-file projection failure.

Source transitions use a capacity-one blocking stream and are ordered and non-conflated. Generic latest-value conflation is unsafe because heterogeneous transitions may erase one another: in particular, an Observation Error must not replace a pending Projection before Gateway adopts the valid list. Filesystem debounce and unchanged-content fingerprinting bound ordinary volume; every distinct successfully projectable content version produces a Projection even when it is semantically equal to the effective Projection. Gateway Runtime synchronously adopts the first transition and starts its own consumer for later transitions before construction completes, independently of listener serving, so the producer cannot stall before `ServeReady`. Runtime close closes Source, drains and joins that consumer, and only then completes. Any later suppression or coalescing must be justified by measurements and use Source-specific rules that never let diagnostics erase a Projection or terminal observation failure.

Start Guidance and Runtime Status expose optional Upstream List Diagnostics rather than one degradation cause. The compound detail independently carries an Invalid Format cause and an Observation Error kind and cause, and is absent when both are clear. The first transition uses the same state reducer as later transitions but establishes the constructor baseline without publishing notifications. Every Projection consumed afterward publishes a conflated status invalidation even when semantically equal to the effective Projection, while a Managed PAC desired state is published only when routing changes. The same notifications apply while activation is starting as while running; Start uses fresh snapshots at its existing installation and result boundaries rather than coupling Source consumption to activation phase. Runtime desired-state and status-notification streams remain open and their consumers terminate through lifecycle context rather than treating channel closure as a lifecycle signal.

Inbound Adapters render coexisting diagnostics independently: the current Observation Error comes first with recovery guidance derived from its kind, followed by Invalid Format as the retained projection assessment. They never merge the two causes. The clean break removes `ListAccepted`, `SourceDegraded`, `UpstreamListDegradationDetail`, the old JSON field, and related helpers without aliases or fallback decoding.

The three recognized Source transitions carry diagnostic causes without implementing Go's `error` interface, and a correctly reported terminal Observation Error is non-fatal. An unknown transition or a Source stream that closes without a terminal Observation Error when Runtime did not request closure is instead an internal protocol violation: construction fails and rolls back when detected initially, while live consumption reports it through Runtime's fatal path for coherent shutdown. This distinction prevents programmer errors from silently preserving stale routing without turning observation failure into runtime failure.

Runtime close is one idempotent transaction shared by explicit stop, serving cancellation, fatal failure, activation rollback, and direct cleanup. Concurrent callers wait for the same cached joined result: Runtime marks closing, closes Source, drains and joins the Source consumer, then closes proxy and PAC traffic resources.

Configuration Bootstrap and Source observation are independent Upstream List operations orchestrated by Gateway. Missing-file creation requires explicitly disclosed, fingerprint-bound Start consent presented separately from and before Managed PAC Consent; acceptance invokes synchronous exclusive Bootstrap, whose error becomes a non-persistent warning on that Start result without preventing Start. Gateway Runtime then opens, consumes, and closes the Source independently of listener serving and without an ownership handoff from Start. Active observation reports its own diagnostics and detects later user correction, whereas terminal observation preserves its cause and requires repair plus Gateway restart without stopping the already-serving runtime. seamless-cors never replaces, repairs, rewrites, or recreates the user-managed `upstreams.txt` outside authorized Bootstrap.
