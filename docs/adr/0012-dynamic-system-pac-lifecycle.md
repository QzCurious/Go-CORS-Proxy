# Dynamic System PAC lifecycle

Status: accepted

This decision supersedes the PAC integration and Stop-cleanup portions of ADR-0001, ADR-0002, ADR-0006, ADR-0009, and ADR-0011. The previous activation-scoped Control and fixed service set made lifecycle and reporting more complex without protecting additional user state, so they are replaced by one deep System PAC module exposing three synchronous operations: deliver to a required PAC Endpoint, observe with an optional current PAC Endpoint, and clean up owned PAC state. System PAC owns publication generation, current Network Service discovery, PAC ownership classification, safe mutation, serialization, and verification; the separate Network Service module continues to hide platform mechanics.

Every System PAC Delivery allocates a new publication generation, freshly observes every currently visible Network Service, changes only empty or marker-owned settings, and freshly verifies the resulting state. Foreign and unobservable settings are preserved, successful services are not rolled back, and failed or partially successful attempts consume their generation. Initial start, every effective Traffic Projection change, and repeated start each request their own serialized delivery through ordinary backpressure; requests are neither conflated nor retried by background polling. Delivery failure, including having no safely mutable service, does not prevent Gateway Runtime from starting or continuing.

System PAC returns its available facts together with concrete discovery, observation, mutation, or verification errors. Gateway owns the resulting surface-neutral System PAC Report, retains exactly one latest delivery report as historical diagnostics, and asks System PAC for fresh observation when producing current status. Observation always reports every visible Network Service and can classify Routes Current Endpoint only when given a current endpoint; foreign PAC is ordinary excluded state rather than drift or failure.

Every `stop` attempts System PAC Cleanup and Gateway State Cache cleanup whether it finds a start-hosted owner, a router-only `serve` owner, or no owner. With a live runtime, delivery triggers are cancelled and System PAC Cleanup runs while traffic endpoints still serve, after which runtime and owner shutdown continues. Cleanup disables and verifies active marker-owned settings while preserving foreign, disabled, and unobservable settings. Discovery, observation, mutation, or verification uncertainty makes the cleanup sub-operation unfulfilled and is prominently reported, but Stop itself remains fulfilled and exits successfully after its best-effort attempts. There is no separate cleanup command or previous-PAC restoration.

The clean break removes the old Control model, terminal PAC-specific Start outcomes, generic runtime-status notifications, and the conflating stream helper; UserCA assessment and System PAC delivery use separate ordinary channels.
